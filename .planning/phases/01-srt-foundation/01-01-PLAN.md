<objective>
Build the SRT parsing foundation: a pure function pipeline that reads raw bytes, detects encoding, decodes to UTF-8, and parses SRT content into structured Cue objects with defensive error handling.

Purpose: This is the data foundation for the entire app. Every subsequent phase (playback, persistence, display) depends on the Cue[] structure produced here. Encoding resilience is critical — Chinese SRT files in GBK/Big5/Shift-JIS must decode correctly or the app is unusable for its primary audience.

Output: Types (Cue, ParsedSubtitle, ParseError), encoding detection module (chardet + TextDecoder), SRT parser (custom, ~50 lines), all tested and verified.
</objective>

   - Stage 1: Check UTF-8 BOM (bytes 0xEF, 0xBB, 0xBF) → decode with TextDecoder('utf-8'), strip first 3 bytes, return encoding: 'UTF-8 (BOM)'
   - Stage 2: Try UTF-8 fast path with `new TextDecoder('utf-8', { fatal: true })` → if succeeds without throwing, return { text, encoding: 'UTF-8' }

   - Stage 5: Decode with `new TextDecoder(encoding, { fatal: false })`, return { text, encoding }
   - Import chardet as `import chardet from 'chardet'`

**Critical:** chardet.analyse receives raw Uint8Array, NOT a decoded string. TextDecoder is native browser API — no import needed.

  <action>
1. Create `src/imports/srtParser.ts` with:
   - `parseSRT(content: string): ParsedSubtitle` pure function
   - Step 1: Normalize line endings — `content.replace(/\r\n/g, '\n').replace(/\r/g, '\n')`
   - Step 2: Strip BOM character — `content.replace(/^\uFEFF/, '')`
   - Step 3: Split into blocks by double-newline — `content.split(/\n\n+/).filter(b => b.trim().length > 0)`
   - Step 4: For each block, split into lines, find timecode line (contains '-->')
   - Step 5: Parse timecode with regex accepting both dot and comma: `/(\d{2}):(\d{2}):(\d{2})[,.](\d{3})\s*-->\s*(\d{2}):(\d{2}):(\d{2})[,.](\d{3})/`
   - Step 6: Convert timecode to milliseconds: hours*3600000 + minutes*60000 + seconds*1000 + ms
   - Step 7: Text is everything after timecode line, joined with \n, trimmed
   - Step 8: Push Cue with sequential id (cues.length + 1), start, end, text
   - Step 9: Collect errors for invalid timecodes, empty text blocks (never throw)
   - Step 10: Return { cues, metadata: { fileName: '', encoding: '', cueCount: cues.length, parsedAt: Date.now() }, errors }

**Critical:** Parser must NEVER throw on a single bad cue. Collect errors per-cue and continue. Only the caller (importSRT in Plan 2) decides what to do with zero-cue results.

**Edge cases to handle:**
- Missing sequence numbers (don't require them, use array index + 1)
- Extra blank lines between blocks
- Timecodes with dot instead of comma separator
- Multi-line subtitle text (preserve \n in text field)
- Blocks with no timecode line (skip with error)
- Empty text blocks (skip with error)
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User's file system → Browser | Untrusted SRT file content enters via FileReader API |
| Raw bytes → Decoded string | Encoding detection processes untrusted byte sequences |
| Decoded string → Parsed Cue[] | Parser processes untrusted text content |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Denial of Service | fileImport (Plan 2) | medium | mitigate | File size validation (5MB cap) in fileImport.ts |
| T-01-02 | Denial of Service | srtParser | high | mitigate | Defensive parser: per-cue error handling, never throw on single bad cue, collect errors array |
| T-01-03 | Tampering | subtitle text content | medium | mitigate | Render via textContent (not innerHTML) in Phase 2 — Phase 1 stores raw text, Phase 2 must sanitize on render |
